# LastKey — V1 Essence & Rebuild Brief

> **Status:** V1 is complete and paused as of 2026-06-30. It validated the product logic and the data model.
> The backend logic works and is worth carrying forward. The frontend was built MVP-style — inline styles,
> two ~1,000-line page files, layout decisions made mid-build — and should be rebuilt, not refactored.
>
> **Purpose of this document:** capture everything V1 proved, so a V2 can be rebuilt with proper structure
> without rediscovering the business rules, the edge cases, or the reasons behind them.

---

## 1. What LastKey Is

A **two-sided, same-night hotel room bidding marketplace.**

A guest browsing tonight's unsold rooms names the price they'd pay. That private offer goes to the hotel,
which accepts, counters, or declines within a short window. If accepted, the guest gets a confirmation
code and **pays the hotel directly at check-in** — LastKey never touches the money.

### The strategic mechanic (this is the whole business)

Hotels are contractually bound by **OTA rate parity** clauses: they can't publish a rate lower than what
Booking/Expedia show. LastKey sidesteps this because **the guest initiates the price, privately.** The
hotel is not publishing a discounted rate; it's accepting a one-to-one offer. Published rates never move.

This is the reason the product can exist, and every design decision should protect it:
- Offers must stay **private** — never a public "deal" or a visible discount off rack.
- The **guest** must always be the one who names the number first.
- The hotel's floor price must remain **hidden** from guests (see §5, "Bid floor").

### Pilot context
- Pilot market: **Greater New Orleans** (Slidell, LA).
- 2 pilot hotels, ~6 room types.
- Business model: flat fee to hotels during pilot, **no commission**. (Final pricing undecided.)

## 3. Data Model (CARRY THIS FORWARD — it works)

Postgres via Supabase. All tables have **RLS enabled**. `auth.users` is the identity source for both roles.

### `hotels`
| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `owner_user_id` | uuid → auth.users | **NULL means nobody can manage the hotel.** See known issues. |
| `name`, `location`, `city`, `tagline` | text | `location` = street address, `city` = "Slidell, LA" |
| `rating`, `review_count` | numeric(2,1), int | |
| `google_place_id` | text | For the Google reviews widget |
| `deposit_amount` | numeric, default 0 | **Informational display only.** SQL comment enforces intent: never aggregate into revenue/analytics. Collected by the hotel at check-in, never by LastKey. |
| `phone` | text | Informational |

### `rooms`
| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `hotel_id` | uuid → hotels ON DELETE CASCADE | |
| `name`, `room_type`, `sqft`, `floor` | | `floor` = building floor, never shown to guests |
| `rack_rate` | numeric NOT NULL | Public reference price |
| `bid_floor` | numeric NOT NULL | **SECRET.** Column-level `SELECT` is revoked for `anon`/`authenticated`; reachable only via the `owner_rooms()` RPC. |
| `amenities` | text[] | |
| `inventory_count` | int NOT NULL default 1 | Manually managed by the hotel |
| `available_tonight` | bool | Mirrors `inventory_count > 0`; maintained in JS, not by a trigger |
| `is_active` | bool | Soft-delete flag |
| `image_url` | text | Owner-uploaded photo (Storage) |

### `requests` (the core table)
| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `hotel_id`, `room_id`, `guest_id` | uuid FKs | `guest_id` → `auth.users` |
| `bid_amount` | numeric NOT NULL | What the guest offered |
| `counter_amount` | numeric | What the hotel countered at |
| `status` | text NOT NULL default `'pending'` | CHECK: `pending, countered, accepted, declined, expired, handled, cancelled` |
| `confirmation_code` | text | 6-char, generated on accept |
| `expires_at` | timestamptz NOT NULL, **default `now() + 60s`** | Server-authoritative |
| `stay_date` | date NOT NULL default CURRENT_DATE | |
| `created_at`, `resolved_at` | timestamptz | |

Indexes: PK, `hotel_id`, `guest_id`, `room_id`, plus partial `requests_open_expiry_idx (status, expires_at) WHERE status IN ('pending','countered')`.

### `guest_profiles`
`id` (uuid PK → auth.users ON DELETE CASCADE), `name`, `first_name`, `last_name`, `phone`, `rating` numeric(2,1), `stays_count` int, `created_at`.
> `stays_count` is **stale/unused** — real stay counts are derived by counting accepted/handled requests.

### `saved_hotels`
`id`, `guest_id` → auth.users, `hotel_id` → hotels, UNIQUE `(guest_id, hotel_id)` (required for the upsert).

### `images`
`id`, `hotel_id`, `room_id` (nullable — NULL means hotel-level hero), `url`, `position`. Legacy; `rooms.image_url` is the newer path.

### Storage
Bucket `room-images`, **public**. Path convention `{hotelId}/{roomId}/cover` — one stable key per room, upserted, so re-uploads overwrite and no orphans accumulate. Saved URL gets a `?v=<timestamp>` cache-buster.

## 4. Server-Side Logic (CARRY THIS FORWARD — this is the crown jewel)

V1's most valuable output. **Business rules live in the database, not the client**, so they can't be bypassed by a hacked frontend or a second client. A V2 frontend can be swapped in wholesale without touching any of this.

### Triggers on `requests`

| Trigger | Timing | Does |
|---|---|---|
| `trg_auto_decline_below_floor` | BEFORE INSERT | If `bid_amount < rooms.bid_floor`, sets status `declined` + `resolved_at`. Uses `<` so bidding **exactly** the floor is accepted. |
| `trg_enforce_one_open_request` | BEFORE INSERT | Rejects if the guest already has a request that is `pending`/`countered` **AND `expires_at > now()`**. The expiry check is deliberate — it means a lapsed row never wrongly blocks a guest, which is what makes a once-daily cleaner safe. |
| `trg_enforce_response_window` | BEFORE UPDATE OF status | Blocks `accepted`/`declined` once `expires_at < now() - 5s`. **Countering is deliberately still allowed after expiry** (revive-by-counter). Also blocks a revival if that guest has another live request. |
| `trg_stamp_counter_expiry` | BEFORE UPDATE OF status | On transition to `countered`, restamps `expires_at = now() + 120s`. |
| `trg_decrement_inventory_on_accept` | AFTER UPDATE OF status | On transition to `accepted`, `inventory_count = greatest(count-1, 0)` and syncs `available_tonight`. Guards double-fire via `old.status IS DISTINCT FROM 'accepted'`. |

**Trigger ordering matters** — Postgres fires same-timing triggers alphabetically. `enforce_response_window` runs before `stamp_counter_expiry`, so enforcement reads the *old* expiry before it's restamped. Preserve this if renaming.

### SECURITY DEFINER functions
- `owner_rooms()` — returns the owner's rooms **including `bid_floor`** (the only path to that column). Granted to `authenticated`.
- `guest_card_stats(g_id)` — a guest's **global** stay count/rating across all hotels (a hotel's own RLS can only see its own requests). Gated: caller must own a hotel the guest has bid with. Granted to `authenticated`.
- The five trigger functions have `EXECUTE` **revoked** from `public`/`anon`/`authenticated` — otherwise Supabase's advisor flags them as callable RPCs.

### Scheduled job
`pg_cron`: `finalize-expired-requests`, daily at 04:05 UTC — flips lapsed `pending`/`countered` rows to `expired`. Pure hygiene; nothing user-facing depends on it because the UI derives expiry live.

### RLS model
- **Public read** on `hotels`, `rooms`, `images` (browse without an account).
- **Owner-scoped writes** on `hotels`, `rooms`, `images` via `owner_user_id`.
- `guest_profiles`: self full access + a hotel may read a guest's profile **only if that guest has bid with them**.
- `requests`: guest reads/inserts own; guest may UPDATE **only** `countered → accepted|declined`; hotel owner reads/updates all for their hotel.
- `saved_hotels`: self only.
- Storage `room-images`: owner-only writes, path's first folder segment must be a hotel they own. Public bucket, deliberately **no SELECT policy** (a broad one would let anyone list every file).

## 5. Core Business Rules (the essence to preserve)

**Bid lifecycle**
```
guest submits ──> [auto-decline if < bid_floor] ──> declined (terminal, instant)
              └─> pending (60s)
                    ├─ hotel accepts  ──> accepted  (+ confirmation code, inventory decrements)
                    ├─ hotel declines ──> declined  (terminal)
                    ├─ hotel counters ──> countered (120s) ─┬─ guest accepts ──> accepted
                    │                                        └─ guest declines ─> declined
                    └─ window lapses  ──> expired
                                            └─ hotel may COUNTER to revive ──> countered (fresh 120s)
```

**Timing**
- Guest bid → hotel response: **60 seconds** (`TIMER_SECONDS`).
- Hotel counter → guest response: **120 seconds** (`COUNTER_TIMER`).
- 5-second grace on enforcement, absorbing round-trip latency.
- `expires_at` is **always server-set** (column default / trigger). Never trust a browser clock — at 60s, skew is 10× more damaging than it was at 600s.
- The UI derives "expired" live in the browser via `effectiveStatus()`, so display is instantly correct regardless of whether the cleaner has run.

**Money**
- LastKey **never** processes payment. Guest pays the hotel at check-in.
- Tax shown to guests is an **estimate only** (`TAX_RATE = 0.14`).
- Security deposit is **informational** — a hold the hotel collects, explicitly excluded from every revenue/analytics calculation.
- Confirmation code proves the rate, **not** room condition or availability guarantees.

**Bid floor (hidden minimum)**
- Per room. Bids below it auto-decline before reaching the front desk.
- **Never exposed to guests** — column-level grant revoked, guest-facing queries never select it. If guests learned the floor, everyone would bid exactly the floor and hotels would capture zero surplus.
- Real pilot data: floors sit **38–60% below rack**.

**Inventory & oversell**
- Inventory is **manually managed by the hotel**. No nightly auto-reset (explicit decision).
- Accepting decrements by 1, never below 0.
- Overselling is **allowed** — it's the hotel's call. The system *warns* (sold-out banner, "Accept anyway" + confirm) but never blocks. Rationale: the hotel may have inventory the system doesn't know about.

**One active request per account**
- A guest may have only one live request at a time, **across all hotels** (not per hotel).
- Enforced in the DB, not just the client.
- **No cancel** — the window is too short to be worth one. (V1's cancel button was also silently broken by RLS for its entire life.)

**Roles**
- One browser session, one Supabase session, two portals. A hotel-owner account visiting the guest site gets a guard screen rather than a guest profile.
- Guests are identified to hotels **only** by star rating and stay count — never name, email, or phone.

**Booking day**
- `getTodayKey()` uses a **6 AM boundary**: between midnight and 5:59 AM it returns the previous calendar date, since "tonight" spans midnight. Used consistently for stats, calendars, and stay dates.

## 7. Why We're Rebuilding (honest assessment)

**What's wrong is the frontend, not the domain.**

1. **Two god-files.** `pages/index.js` (1,518 lines) holds every guest screen — listing, detail, bid, confirm, waiting, counter, result, live, history, saved, profile — plus the header, footer, and homepage marketing. `pages/hotel.js` (884) is the same story. Only **one** component was ever extracted.

2. **Screen state is a string, not a route.** `screen` ("listing" | "hotel" | "bid" | "confirm" | "waiting" | "counter" | "result" | "login") plus a parallel `sideTab` ("browse" | "live" | "history" | "saved" | "profile"). Consequences seen in practice:
   - **No URL for anything.** Can't link to a hotel, can't refresh mid-flow, back button doesn't work.
   - The two state variables silently conflict — a real bug shipped where `setSideTab("live")` after submitting made the render gate show the side panel *instead of* the result screen, so auto-declined bids never showed their denial screen. Invisible for weeks.
   - Scroll position leaked between screens (needed a manual reset effect).

3. **Styling was invented as we went.** Inline style objects with a growing `SL` bag. At audit: **55 distinct hex colors, 20 font sizes, 15 gap values, 8 raw radii.** Eleven greens for one semantic idea. Consolidated late into `lib/tokens.js` (radius/elevation/border/color), which proved the model works — but spacing and typography scales were never done. Design feels choppy because it *is* choppy: it accreted.

4. **Dead code from pivots.** An entire dark theme (`S` object, ~47 entries) lived on after the app went light, feeding `light={true}` branches that were never false. Removed late.

5. **No tests, no types, no CI.** Every regression was caught by hand or by the user. Several bugs shipped and survived because nothing checked them.

6. **Verification gaps.** Business logic was proven with SQL rollback transactions (good), but UI behavior was only ever eyeballed.

**What went right and should be repeated:**
- Business rules pushed into Postgres (triggers + RLS) rather than the client.
- Secrets kept server-side behind API-route proxies.
- Migrations written to files *and* applied, with the security advisor run after every RLS/policy change.
- A single `lib/api.js` boundary — the entire data layer is already portable to a new frontend.

## 8. V2 Rebuild Recommendations

**Keep wholesale:** the database, all triggers/functions/RLS, the storage layout, and the domain rules in §5. Treat `lib/api.js` as the spec for the data layer.

**Change:**

| Area | V1 | V2 |
|---|---|---|
| Routing | `screen` string state | Real routes: `/hotel/[id]`, `/bid/[roomId]`, `/requests` — URLs, refresh, back button |
| Router | Pages Router | App Router (server components for browse/detail; client only for the bid flow) |
| Types | None | TypeScript, with DB types generated from Supabase |
| Styling | Inline objects + `SL` bag | One system (Tailwind or CSS modules) driven by tokens — define spacing + type scales **before** building |
| Components | 2 god-files | Real component tree; no file over ~300 lines |
| Data | Ad-hoc `useEffect` + manual refetch | A query library (TanStack Query) for caching, refetch, realtime invalidation |
| Timers | Two competing effects + `now` ticker | One countdown hook, server-time aligned |
| Tests | None | At minimum: bid lifecycle state machine, expiry math, floor logic |
| Secrets | 2 proxied routes | Same pattern; never a service-role key in the client bundle |

**Structural rules worth setting up front:**
- The bid lifecycle is a **state machine** — model it explicitly rather than as scattered `if (status === …)` checks.
- Server time is authoritative; the client only *displays* countdowns.
- Every guest-facing query must be incapable of selecting `bid_floor`.
- Money formatting, tax, and the 6 AM booking-day rule belong in one shared module.

## 9. Open / Unbuilt Features (backlog)

### Committed but not built
- **Email notifications to hotels on a new bid.** Designed, not implemented. Supabase DB Webhook → API route → Resend. **Blocker:** Resend's free tier needs a verified sending domain to email arbitrary addresses. Also needs `hotels.notify_email` (fall back to owner's auth email).
- **Guest email on counter received** — without it, a revived bid is invisible to a guest who closed the tab, which defeats revive-by-counter.
- **`/for-hotels` real contact method** — currently a placeholder `mailto:`.
- **Legal copy** for `/privacy` and `/terms` — structure exists, all bodies are `{LEGAL COPY PENDING}`.

### Known gaps / decisions pending
- **The 60s window vs. no alerting.** A hotel not watching the dashboard misses the bid. Data is never lost (it stays in Reservations/KPIs) but becomes non-actionable. Revive-by-counter is the mitigation; SMS is the real fix if volume warrants.
- **Retry guidance is wrong.** The declined-bid tip says "bids within 20% of the listed rate" — but real floors are 38–60% below rack. It pushes guests to overpay or give up. Three options were on the table: fix the copy generically, nudge with a server-computed suggested amount (no floor leak), or reveal a minimum. **Undecided.**
- **Auto-declined bids are invisible to hotels.** Below-floor bids never reach the dashboard, so hotels never learn demand existed. Likely higher volume than timeouts. Same counter mechanism could surface them.
- **Days Inn Slidell has `owner_user_id = NULL`** — nobody can manage it, upload photos, or receive alerts. An unapplied migration (`20260630000000_assign_daysinn_owner.sql`) would assign it to the founder account. **Pending decision.**
- **Homepage A/B undecided** — `HomeSuitely.js` (`?home=v2`) still lives alongside the default. Pick one and delete the other.
- **Design tokens half-done** — color consolidated; **spacing and font-size scales never built**.
- **Oversell** is permitted by design; no reconciliation flow if it happens.
- **No nightly inventory reset** (deliberate) — hotels must re-stock manually each evening or listings go dark.

### Future features (not started)
- **Google OAuth sign-in.** Explicitly planned. `/privacy` exists specifically because Google's verification requires a live policy URL. **V1 and near-term stays email + password.**
- SMS alerting (Twilio) for hotels.
- Internal review system — guests currently have ratings but there's no way to leave one. Google reviews are read-only display.
- Multi-city expansion — data model supports it; UI has hardcoded pilot constants (`PILOT_CITY_LABEL`, `CITIES`, `CITY_COORDS`).
- Property types beyond hotel rooms — the homepage shows Flats/Hostels/Villas tabs as "Coming soon".
- Guest-side push/email on bid resolution.
- Hotel-side analytics beyond the current single-day KPI panel.
- Payment/deposit handling (deliberately out of scope — deposit is informational only).

### Known long-standing advisor warnings (accepted)
- `owner_rooms()` and `guest_card_stats()` are SECURITY DEFINER and callable by `authenticated` — **intentional**, both are ownership-gated.
- Leaked-password protection disabled in Supabase Auth — worth enabling.

### Terminology
- **Rack rate** — the public reference price.
- **Bid floor** — hidden per-room minimum; below it, auto-decline.
- **Request / bid** — same thing; the table is `requests`.
- **Handled** — a legacy status treated as equivalent to `accepted`.
- **Tonight** — the 6 AM-boundary booking day.
